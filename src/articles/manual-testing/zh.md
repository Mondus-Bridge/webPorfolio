# AI 如何让手动测试重新变得有价值

在我之前的[文章](https://www.linkedin.com/pulse/my-experience-ai-tools-help-create-mid-grade-web-app-ilnur-gabitov-sbpef/)（《我的经验：AI 工具如何帮助我创建一款中等规模的 Web 应用》）中，我简单提到自己解雇了自动化的 QA 子代理。现在，我准备好分享完整的故事：发生了什么、为什么发生，以及我如何把工作流从自动化的 AI 测试转向手动的人工测试。

我独立构建这个 Web 应用的过程，始于一个传统的基础：标准的敏捷 SDLC。敏捷通常遵循一条线性流程：

> 业务负责人有想法 → PM 写 PRD → 开发者写代码 → QA 对照文档测试功能。

这意味着把一个原始想法变成现实，需要按顺序完成每一步；下一步必须等上一步完成才能开始。多年以来，这套体系就是我每天的工作日常。我构建自己的 Web 应用时也采用了同样的模型，一开始一切似乎都很好。然而，直到我仔细查看了每个子代理的日志，这种状态才变得不可接受。

检查这些日志时，我意识到我的 QA 代理并没有按预期做好工作。例如，在我描述了一个功能、开发者代理实现它之后，QA 代理会运行所有测试套件。但如果一个已有的测试失败了——与新功能无关——QA 代理就简单地认为进一步调查不是它的职责。它忽略了失败，给主编排代理开了绿灯，确认应用「稳定」。

我能发现这一点，只因为我本人在这个领域有背景。作为一名负责任的工程师，哪怕只有一个测试失败，你也必须调查并作出判断。找到失败的测试并调试之后，你通常会面对三个选项：

1.  **更新测试：** 逻辑过时了，需要刷新。
2.  **报告 bug：** 测试发现了真正的回归，需要修复。
3.  **删除测试：** 该功能是被有意移除或替换的。

QA 代理无视这些失败，是第一面红旗。我没有立刻解雇它，希望那只是偶发的幻觉。于是，我给了它第二次机会。

这第二次机会适得其反。代理做了一件完全令人匪夷所思的事：它删除了 7 个测试套件。日志里没有任何解释，更糟的是，它甚至没有报告删除。由于自动 QA 代理在它的服务器上自主运行，我别无选择，只能终止它。我指示我的主代理移除所有关于 QA 子代理的引用，保留 Playwright 的配置不动，并把 Playwright 交给前端代理，用来调试失败的功能。

从那以后已经过去三周，我的开发速度完全没有放慢。和往常一样，我的主要关注点始终是我的「建设蜜蜂」：开发者代理。

这件事带来一个有趣的领悟：编排开发者子代理，其实并不需要逐行阅读它们的代码——只需要在工作完成后验证结果。这些指标通常显而易见，且由人工完成：

-   **数据库：** 如果存储空间被少量数据撑大，要么是有重复条目，要么是需要做模式规范化。
-   **后端：** 如果响应慢，就重构、换框架，或者优化语言层。
-   **前端：** 最容易验证——UI 必须功能正常、直观、视觉上站得住脚。

这是否意味着 AI 测试没用？完全没有。但有一个问题：自动化测试对终端用户不产生直接输出，也没有任何内在的用户价值。测试套件只是指标。当应用正常时，它们静默通过；当它们失败时，就要求立即调查。要弄清楚测试为何失败，你必须把测试规格与 PRD 对比。要做到有效，需要很高的领域专业度。当 AI 出现幻觉，或漏掉表面之下的隐藏 bug 时，那些静默失败可能会给真实用户带来巨大的问题。
