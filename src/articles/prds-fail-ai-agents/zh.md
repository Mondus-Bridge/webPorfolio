# 为什么 PRD 在 AI 智能体面前失效：为智能体工作流结构化文档

人类语言依赖高层次的抽象，而代码要求精确的操作逻辑。在管理 AI 编码智能体时，这种差距会导致输出错位和永无止境的提示词迭代。要弥合这一差距，你需要两样东西：结构化的领域词汇表，以及清晰定义的项目边界。

在传统软件开发（SDLC）中，产品需求文档（PRD）充当开发人员与业务利益相关者之间的「唯一事实来源」。虽然标准的 PRD 对人类工程师有效，但在 AI 智能体面前却会失效。机器不需要高层次业务意图——它们需要的是情境护栏和明确的操作规则。

在智能体工作流中，文档不应仅仅作为静态的事实来源去说明要构建什么；它必须解释系统是如何组织的，这样你才能保留对生成过程的控制权。

为了验证这个想法，我尝试运行了 [Matt Pocock 的 /to-prd 工作流](https://www.skills.sh/mattpocock/skills)，但它很快就变成了一个时间黑洞。

最初的[建议是自动生成 PRD 并跳过评审](https://www.youtube.com/watch?v=-QFHIoCo-Ko)，几个月后建议又转向[「删除大部分文档」，理由是文档漂移](https://www.youtube.com/watch?v=Fj8DKMbdIzU)。从一开始，如果 Matt Pocock 建议完全跳过文档评审，那么认真对待他在文档方面的建议就毫无意义。

测试证实了我的怀疑：传统的 PRD 在 AI 智能体面前失效，因为它们是为人脑理解而写的，而非为机器执行而写。机器工作流需要结构化的领域术语和严格的项目分层约束，而不是静态的 PRD 模板。

因此，我直接在仓库中构建了一个明确结构化的机器知识库：

1. **「文件夹到智能体」映射（docs/README.md）**
   我没有把全部上下文都塞进提示词，而是提供了一个专门的索引，把功能区域直接映射到文件。当智能体听到「weapon picker」或「canonical mode」这样的领域术语时，它就知道该按需阅读 docs/ 下的哪份文档。

2. **严格的机器护栏（AGENTS.md）**
   我在每个层级（根、后端、前端、e2e）都定义了明确的约定。例如，frontend/AGENTS.md 要求每个交互元素都有稳定的 snake_case ID（如 theme_toggle_button、history_table）。这为智能体在生成 UI 代码或运行 Playwright 测试时提供了精确的目标。

3. **硬性单一事实来源**
   - **API 契约：** docs/api/openapi.yaml 充当严格契约——后端逻辑以此为基准进行测试，前端类型则从中自动生成。
   - **领域数学与上游引用：** 数学模型和公式（如元素反应与伤害公式）被隔离在 docs/domain/ 下，防止智能体「凭空捏造」游戏物理。

4. **聚焦的交接简报（requirements.md）**
   每当我启动一个新的子智能体时，一份自包含的架构简报会为它提供当前的设计状态，这样它就不会浪费 token 去重新推导整个 monorepo 的结构。

话虽如此，在防止文档漂移方面仍有明显的改进空间。在我自己的项目中，一次快速审计发现，智能体的提示词仍然引用了几个已删除的文档和过时的文件名。此外，一些关键的自动化步骤——比如直接从 openapi.yaml 生成 TypeScript 类型——并没有完全记录在索引中。收拢这些疏漏，才能确保「精准定位」系统对新智能体保持 100% 可靠。

机器不需要华而不实的业务需求；它们需要结构化的领域词汇、精确的文件/元素路径，以及清晰的操作边界。

如果你想要可预测的代码生成，不要只改进提示词——要为机器摄取来架构你的文档。
